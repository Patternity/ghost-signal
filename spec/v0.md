# GhostSignal Protocol v0

**Status:** Draft  
**Version:** 0  
**Scope:** Media-embedded data transmission  
**Layers:** Transport / Data  

---

## 1. Overview

GhostSignal is a protocol for embedding and extracting structured data directly from media streams (video, audio).

The protocol treats media as a **self-contained data field**:
- data is carried *inside* the media stream,
- decoding requires access to the original media artifact,
- modification or truncation of the stream MAY invalidate the data.

GhostSignal v0 defines:
- a **Transport Layer** (how data is physically embedded),
- a **Data Layer** (how data and metadata are structured and interpreted).

Cryptography, compression, and authentication are explicitly **out of scope** for v0.

---

## 2. Layer Separation

### 2.1 Transport Layer

The Transport Layer defines:
- where the data channel exists inside the media,
- how bits and bytes are physically encoded,
- how much data can be transmitted per frame.

Transport parameters are **out-of-band**:
- a decoder MUST know or discover the transport profile before decoding,
- transport parameters are NOT transmitted inside the data stream.

### 2.2 Data Layer

The Data Layer defines:
- stream layout and decoding rules,
- metadata (META),
- payload format and integrity checks.

The Data Layer is transmitted **in-band** using the Transport Layer.

---

## 3. Transport Layer (v0)

### 3.1 Reference Transport Profile: VBB-8

GhostSignal v0 defines a single reference transport profile:

**Name:** VBB-8 (Visible Byte Band)

**Properties:**
- Anchor: bottom of the video frame
- Band width: full frame width
- Band height: 4 grid rows
- Cell size: 8×8 pixels
- Byte block: 2×4 cells (8 bits per byte)
- Bit order: MSB first, row-major within the block
- Encoding: binary (black = 0, white = 1)

**Capacity per frame:**
```

bytes_per_frame = floor( frame_width / (cell_size_px * byte_block_width) )

```

### 3.2 Transport Assumptions

- The transport profile is fixed for the entire stream.
- If the transport cannot be decoded, no metadata or payload can be decoded.
- Transport discovery mechanisms are out of scope for v0.

GhostSignal v0 defines a single reference transport profile for video streams.
Audio transport profiles are explicitly out of scope for v0 and may be defined in future versions as independent transport specifications.

---

## 4. Data Layer (v0)

### 4.1 Stream Layouts

GhostSignal v0 defines two stream layouts.

#### 4.1.1 SECURE Layout

Purpose: strict, artifact-bound data delivery.

- Metadata (META) is transmitted **only at the beginning** of the stream.
- If the META window is lost or modified, decoding MUST fail.
- Intended for use cases where the media artifact itself is the key.

#### 4.1.2 OPEN Layout

Purpose: resilient, user-friendly delivery.

- Metadata (META) is transmitted at the beginning and periodically later.
- Decoding MAY start after a resynchronization point.
- Intended for analytics and non-strict use cases.

### 4.2 META Window

- META is transmitted during the first `N` frames of the stream.
- META is repeated cyclically within the META window.
- META is encoded using the same transport as payload data.

For v0, `N = 60` frames is RECOMMENDED.

---

## 5. Metadata Format (META)

META is a fixed-format header encoded as raw bytes.

### 5.1 META Structure

| Field | Size | Description |
|-----|-----|------------|
| magic | 4 bytes | ASCII `"GSIG"` |
| version | 1 byte | Protocol version (0x00) |
| layout | 1 byte | `0x00` = SECURE, `0x01` = OPEN |
| payload_length | 4 bytes | Payload length in bytes (uint32, big-endian) |
| payload_crc32 | 4 bytes | CRC32 of the payload |

Total META size: **14 bytes**

### 5.2 META Rules

- META MUST be fully decoded before payload decoding begins.
- META is NOT encrypted or compressed.
- META does NOT include transport parameters.

---

## 6. Payload Format

### 6.1 Payload Encoding

Payload is transmitted as **raw bytes** following META.

- No encryption
- No compression
- No framing beyond META

Payload bytes are read sequentially from the stream.

### 6.2 Payload Structure (TLV)

Payload content is structured as a sequence of TLV records.

**TLV format:**
- `type` — 1 byte
- `length` — 2 bytes (uint16, big-endian)
- `value` — `length` bytes

Example types (non-exhaustive):
- `0x01` — UTF-8 text
- `0x02` — URL
- `0x03` — JSON
- `0x10` — campaign identifier
- `0x11` — coupon code

---

## 7. Payload Completion and Validation

- Payload decoding completes when `payload_length` bytes are collected.
- Decoder MUST verify `payload_crc32`.
- If CRC verification fails, decoding MUST fail.

In SECURE layout, payload placement MAY be designed so that
successful decoding requires access to the full stream duration.

---

## 8. Decoder State Machine (Informative)

Recommended decoder flow:

1. **LOCK TRANSPORT**
   - Select known transport profile (e.g. VBB-8)

2. **READ META**
   - Scan META window
   - Detect `GSIG`
   - Parse META

3. **READ PAYLOAD**
   - Read raw bytes sequentially
   - Accumulate until `payload_length`

4. **VERIFY**
   - Validate CRC32
   - Parse TLV records

---

## 9. Failure Conditions

Decoding MUST fail if:
- transport decoding fails,
- META cannot be decoded,
- payload length is not reached,
- CRC verification fails.

---

## 10. Non-Goals (v0)

GhostSignal v0 explicitly does NOT define:
- encryption or secrecy guarantees,
- compression schemes,
- cryptographic signatures,
- proof-of-human or proof-of-attention.

These may be addressed in future versions.

---

## 11. Forward Compatibility

Future versions MAY introduce:
- additional transport profiles,
- alternative layouts,
- error correction and rateless encoding,
- authentication and verification layers.

v0 decoders MUST ignore unknown payload TLV types.

---

## 12. Summary

GhostSignal v0 establishes a minimal, strict separation between:
- **Transport** — physical embedding of data in media,
- **Data** — structured metadata and payload.

This separation allows the protocol to evolve without breaking the core model:
media as a self-contained data carrier.
